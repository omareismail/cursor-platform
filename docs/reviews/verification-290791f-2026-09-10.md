## V01 — P1: PowerShell quoting and multiline commands still bypass recursive-delete checks

Location: `D:/repos/cursor/.claude/hooks/guard-bash.mjs:174` and line 196.

The tokenizer treats backslash as an escape inside double quotes. PowerShell uses a different escaping model.
Consequently, a quoted Windows root ending in a backslash is parsed incorrectly.

The guard returned allow/exit 0 for both of these command strings:

```powershell
Remove-Item -LiteralPath "C:\" -Recurse -Force
Remove-Item -Recurse -LiteralPath "C:\"
```

It also allowed a multiline string containing `Write-Output ok` followed by the previously blocked
`Remove-Item C:\ -Recurse -Force`. Newlines are not statement boundaries in `splitStatements`, so the second
command is hidden behind the first command's tokens.

These strings were submitted only to the hook in a disposable fixture. No deletion command was executed.
The fixture explicitly disables the platform-development escape.

Required correction: preserve PowerShell quoting semantics and recognize its statement boundaries. Add quoted
drive-root and multiline regression cases. The original argument-order test alone cannot establish this protection.

## V02 — P1: A directory suffix bypasses build-output ownership validation

Location: `D:/repos/cursor/.cursor/tools/build-plugin.mjs:134`, with deletion at line 220.

`resolvePluginOut()` permits an existing directory without a build marker whenever its name ends in `.__check__`
or contains that directory segment. A fixture containing `backup.__check__/important.txt`, with no plugin marker,
was accepted as an output directory. The subsequent build path recursively removes accepted existing outputs.

The test invoked only the path validator; it did not run the recursive deletion.

Required correction: create and track private temporary directories for the current check invocation. User-supplied
output names must not inherit cleanup permission from a suffix. Preserve the marker/ownership requirement for
pre-existing output directories, including those whose names resemble temporary build folders.

## V03 — P1: First push to the default branch can skip all signature checks

Location: `D:/repos/cursor/.cursor/tools/signed-lifecycle-range.mjs:46`; manual-run behavior at line 57.

On a first push, `before` is all zeroes. When a default branch is provided, the helper selects
`origin/<default>..<sha>`. After checkout of the newly pushed default branch, that remote-tracking reference can
already equal the target SHA, producing an empty range.

An isolated Git history contained a lifecycle-changing commit followed by a documentation commit. The normal
before/after range selected the lifecycle commit. With `origin/main` at the new tip, the first-push path selected
none. A manual run on that same default-branch tip also selected none.

Required correction: verify the appropriate reachable history for a newly created default branch instead of
subtracting its post-push reference. Define the intended manual-run scope explicitly and make the output clear
when it verifies no commits. Add these event-shaped cases to the fixture tests.

## V04 — P2: Short database-object names still lose reverse lineage

Location: `D:/repos/cursor/.cursor/tools/feature-map.mjs:597`.

A feature declaring `lineage.calls: ["usp_Settle"]` is accepted, and forward traversal resolves it to the unique
catalog object `dbo.usp_Settle`. However, reverse traversal from `dbo.usp_Settle` reads only the canonical key in
`index.byObject`; the caller was indexed under the short name.

In the reproduction, `lineage settlement` returned the procedure and its table, while `lineage dbo.usp_Settle`
returned an empty feature list. There was only one matching object, so this was not an ambiguous-schema case.

Required correction: resolve accepted aliases to stable object IDs before indexing and reuse that identity logic
for forward traversal, reverse traversal, file queries, and freshness. Define how ambiguous aliases are refused.
