# Skill: test-strategy

**Invocation:** `/test-strategy`

---

## Overview

`test-strategy` decides what each test layer is responsible for, what it is
explicitly not responsible for, and which number proves the product meets the
non-functional requirements from phase 1. It exists because a platform with
several test generators will produce plenty of tests without anyone deciding
what they are for, and the resulting suite has high coverage, slow feedback, and
no answer to "does the quote-to-issue journey work". Written once at the start of
phase 5, it is what Gate 5 evaluates against.

---

## Steps

**Step 1 — Read the inputs.**

`docs/product/nfr.md` (the numbers), `docs/product/story-map.md` (the critical
journeys and their acceptance criteria), `docs/design/architecture.md` (the
seams), `docs/analysis/risks.md` (what must not fail).

**Step 2 — Assign each layer a job, and a boundary.**

| Layer | Owns | Explicitly does NOT own | Generated by |
|---|---|---|---|
| Unit | Domain rules, invariants, calculations | Anything crossing a process boundary | `/dotnet-test-gen`, `/react-test-gen` |
| Integration | Handler to database, real schema | UI behaviour | `/dotnet-test-gen` with TestContainers |
| Contract | Request/response shape per `api-design.md` | Business outcomes | `/dotnet-test-gen` |
| E2E | Critical journeys, real browser, real API | Edge cases (too slow, too brittle) | `/e2e-test-gen` |
| Load | The NFR numbers under concurrency | Correctness | `/load-test-gen` |
| Security | OWASP, authz per endpoint, injection | Business rules | `security-auditor` subagent, `/threat-model` follow-up |
| Compliance | SAMA / ZATCA / mada evidence | Everything else | `/compliance-audit` |

The "does not own" column is the useful one. Without it every layer drifts
upward, E2E ends up testing validation messages, and the suite takes forty
minutes.

**Step 3 — Name the critical journeys, and keep the list short.**

From the story map. These get E2E coverage; nothing else does. A team that
E2E-tests everything has an E2E suite nobody trusts because it is always red for
an unrelated reason.

**Step 4 — Set targets that mean something.**

Line coverage is a floor, not a goal. State it, then state the two that matter:

- **AC coverage: 100%, non-negotiable.** Every acceptance criterion has a test
  asserting it, proven by `node ${CLAUDE_PLUGIN_ROOT}/tools/ac-trace.mjs check`. This is the
  criterion that closes the loop back to phase 1.
- **Mutation score** on domain and application layers, per `templates/mutation/`.
  High line coverage with a low mutation score is the signature of tests that run
  code without constraining it.

**Step 5 — Decide environments and data.**

Where each layer runs, how the database is provisioned, where test data comes
from, and how PII is handled if production data is ever involved. In this domain,
the answer to that last one is usually "it is not" — write that down.

**Step 6 — Set the feedback budget.**

How long the pre-merge suite may take, what moves to nightly when it is exceeded,
and what is allowed to be flaky (nothing) versus quarantined (named, with an
owner and a date).

**Step 7 — Write `docs/testing/strategy.md`.**

Sections: layer responsibilities, critical journeys, targets, environments and
data, feedback budget, and the trace from each NFR to the test that proves it.

## Front-matter — required on every document this skill writes

Open each file with this block. It is the machine-readable half of a
human-written document: the prose stays prose, and `artifact-schema.mjs` reads
this to know what the document is and where it sits in the chain.

```yaml

```

`defines` names the ID prefixes this document **owns**. It is what stops the
first cell of a traceability table being mistaken for a second definition — a
citation of `S-1` in a use-case table is a reference, not a redeclaration.

Validate before reporting done:

```bash
node ${CLAUDE_PLUGIN_ROOT}/tools/artifact-schema.mjs validate
node ${CLAUDE_PLUGIN_ROOT}/tools/artifact-schema.mjs check
```

`check` fails on an ID cited but never defined, and on a chain that stops — a
requirement no story implements, a story no use case covers, a use case no
endpoint serves. Those are gate criteria, computed rather than judged, and
`lifecycle.mjs check` now fails on them too.
